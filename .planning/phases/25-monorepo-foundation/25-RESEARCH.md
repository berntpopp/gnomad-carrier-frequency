# Phase 25: Monorepo Foundation & Core Extraction - Research

**Researched:** 2026-02-24
**Domain:** Bun workspaces monorepo, tsdown library bundling, TypeScript project references, Vitest monorepo config, Vite dev alias
**Confidence:** HIGH (primary sources verified)

## Summary

This phase restructures the existing single-package Vue 3 app into a bun workspaces monorepo with two packages: `packages/core` (`@gnomad-cf/core`) and `apps/web`. The core package receives all pure TypeScript logic (types, queries, filters, calculations, templates, configs), while the web app retains Vue composables as thin reactive wrappers. The key technical challenge is doing this incrementally without breaking the deployed GitHub Pages URL.

The standard toolchain is firmly established: bun workspaces for package management, tsdown v0.20.x for building `@gnomad-cf/core` with subpath exports, Vite resolve alias pointing to core source for dev hot-reload, TypeScript project references for cross-package type checking, and Vitest `projects` array for per-package test runs. All tools are well-documented, actively maintained, and have verified APIs.

The current codebase is already well-positioned for extraction: `src/utils/`, `src/types/`, `src/config/`, and `src/api/queries/` contain zero Vue/Pinia/villus imports and can move directly. The only complication is `src/api/client.ts`, which imports both `villus` and `vue` — it stays in `apps/web` while a new fetch-based client goes into `packages/core/src/client/`. The `src/types/url-state.ts` and `src/utils/exclusion-url.ts` use `zod` and `lz-string` respectively — both become core peer dependencies.

**Primary recommendation:** Create the empty core package structure first, move modules in dependency order (types → config → queries → filters → calculations → templates → client), verify TypeScript compilation after each move, then update web composables last.

### Pattern 1: bun Workspaces Root package.json
**What:** Root package.json declares workspace globs and shared dev dependencies. No `name` field needed (private workspace root).
**When to use:** Always — this is the workspace entry point.
```json
// packages/core root package.json
{
  "name": "gnomad-carrier-frequency",
  "private": true,
  "version": "1.5.0",
  "type": "module",
  "packageManager": "bun@1.3.9",
  "workspaces": ["packages/*", "apps/*"],
  "scripts": {
    "dev": "bun run --filter gnomad-cf-web dev",
    "build": "bun run --filter @gnomad-cf/core build && bun run --filter gnomad-cf-web build",
    "test": "vitest",
    "lint": "bun run --filter '*' lint",
    "typecheck": "tsc --build"
  },
  "devDependencies": {
    "typescript": "~5.9.3",
    "vitest": "...",
    "tsdown": "0.20.3"
  }
}
```
Source: https://bun.sh/docs/install/workspaces

### Pattern 2: tsdown Config for @gnomad-cf/core
**What:** Multiple named entry points produce subpath-importable bundles. `exports: true` auto-updates package.json exports field after each build.
**When to use:** Library packages with tree-shakeable subpath exports.
```typescript
// packages/core/tsdown.config.ts
// Source: https://tsdown.dev/options/package-exports, https://tsdown.dev/options/entry
import { defineConfig } from 'tsdown'

export default defineConfig({
  entry: {
    index:        'src/index.ts',
    types:        'src/types/index.ts',
    config:       'src/config/index.ts',
    queries:      'src/queries/index.ts',
    client:       'src/client/index.ts',
    filters:      'src/filters/index.ts',
    calculations: 'src/calculations/index.ts',
    templates:    'src/templates/index.ts',
  },
  format: ['esm'],       // ESM only — locked decision
  dts: true,             // Generate .d.ts files via rolldown-plugin-dts
  exports: true,         // Auto-update package.json exports field
  clean: true,           // Clean dist/ before each build
  platform: 'neutral',   // Works in Node, Bun, and browser (uses standard fetch)
})
```

### Pattern 3: Vite Dev Alias — Source Resolution Without Build Step
**What:** Map `@gnomad-cf/core` (and subpath variants) to the TypeScript source directory so Vite processes core files directly during dev.
**When to use:** Dev workflow — eliminates the need for a `tsdown --watch` process.
```typescript
// apps/web/vite.config.ts
import { fileURLToPath, URL } from 'node:url'

export default defineConfig({
  resolve: {
    alias: {
      // Intra-app alias (unchanged)
      '@': fileURLToPath(new URL('./src', import.meta.url)),
      // Cross-package: resolve @gnomad-cf/core/* to source
      '@gnomad-cf/core': fileURLToPath(new URL('../../packages/core/src', import.meta.url)),
    }
  }
})
```

**Critical note:** Vite's alias performs simple string prefix replacement. `@gnomad-cf/core/calculations` matches the prefix `@gnomad-cf/core` and replaces it with the source path, producing `../../packages/core/src/calculations`. This works for subpath imports without additional configuration.

**Verify empirically:** After adding this alias, test that `import { calculateCarrierFrequency } from '@gnomad-cf/core/calculations'` resolves alongside `import Something from '@/components/...'`. Both aliases use different prefixes, so there is no conflict — but must be verified with actual dev server startup.

Source: https://vite.dev/config/shared-options (resolve.alias), community patterns verified by multiple Vite monorepo discussions.

### Pattern 6: villus-to-core Query String Bridge
**What:** Core exports GraphQL query strings as `DocumentNode` or plain `string`. Web composables pass them to villus `useQuery`. Core's fetch client also accepts the same strings for CLI use.
**When to use:** Whenever a web composable needs to execute a GraphQL operation.

```typescript
// packages/core/src/queries/gene-search.ts
export const GENE_SEARCH_QUERY = `
  query GeneSearch($query: String!, $referenceGenome: ReferenceGenomeId!) {
    gene_search(query: $query, reference_genome: $referenceGenome) {
      ensembl_id
      symbol
    }
  }
`
```

```typescript
// apps/web/src/composables/useGeneSearch.ts (after extraction)
import { GENE_SEARCH_QUERY } from '@gnomad-cf/core/queries'
import { useQuery } from 'villus'

// villus accepts plain string queries — no DocumentNode needed
const { data, isFetching, error } = useQuery<GeneSearchResponse>({
  query: GENE_SEARCH_QUERY,  // string from core
```

### Pattern 7: bun.lock Text Format Migration
**What:** Current project uses bun 1.3.9 (from `packageManager` field). Bun 1.2 introduced text `bun.lock`. The current lockfile is `package-lock.json` (npm compatibility), not `bun.lockb`.
**Action:** On day one, run `bun install` at root. Check if `bun.lock` or `bun.lockb` is created. If `bun.lockb` (binary), run:
```bash
bun install --save-text-lockfile --frozen-lockfile --lockfile-only
rm bun.lockb
```
`bun.lock` text format is supported by `oven-sh/setup-bun@v2` — the setup-bun repo itself uses `bun.lock` as of Jan 2025.

### Pattern 8: Incremental Module Extraction Order
**What:** Move modules in dependency order to minimize merge conflicts and TypeScript errors.
**Recommended extraction order:**

1. **types** — No upstream imports from `@/` except from `./filter.ts` etc. (self-contained within `src/types/`). Move all `src/types/*.ts` to `packages/core/src/types/`.
2. **config** — Only imports from `./types`. Move `src/config/` to `packages/core/src/config/`.
3. **queries** — Imports types from `@/types` and `@/api/queries/types`. Move `src/api/queries/` to `packages/core/src/queries/`. Query strings are already plain strings.
4. **filters** — Imports from `@/types` and `@/api/queries`. Move `src/utils/variant-filters.ts` + related to `packages/core/src/filters/`.
5. **calculations** — Imports from `@/types` and `@/config`. Move `src/utils/frequency-calc.ts` to `packages/core/src/calculations/`.
6. **templates** — Imports from `@/types` and `@/config`. Move `src/utils/template-renderer.ts`, `src/config/templates/` to `packages/core/src/templates/`.
7. **client** — New fetch-based client (no villus). Move query-execution logic. Keep `src/api/client.ts` (villus) in `apps/web/`.
8. **Update web composables** — Replace `@/api/queries/...` and `@/utils/...` imports with `@gnomad-cf/core/*` imports.

**After each step:** Run `bun run typecheck` to catch import errors immediately.

### Anti-Patterns to Avoid
- **Importing Vue reactivity in core:** Any `import { ref, computed } from 'vue'` in `packages/core/src/` is a violation. The TypeScript compiler will catch this because `vue` is not listed as a dependency of `@gnomad-cf/core`.
- **Using villus in core:** `import { useQuery } from 'villus'` must never appear in core files.
- **Wildcard workspace globs that include apps in packages/*:** Use `"workspaces": ["packages/*", "apps/*"]` (separate globs) — do not put `apps/web` inside `packages/`.
- **Forgetting `"type": "module"` in packages/core/package.json:** tsdown outputs `.mjs` or `.js` ESM; the package must declare `"type": "module"` to use `.js` extensions for ESM.
- **Using `vitest.workspace.ts`:** Deprecated in Vitest 3.2. Use `test.projects` array in `vitest.config.ts` instead.
- **Caching in GitHub Actions without updating cache key:** If you add bun.lock caching in CI, the cache key must include `bun.lock` hash, not `bun.lockb`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| package.json exports generation | Manually maintain exports field | `exports: true` in tsdown.config.ts | tsdown analyzes all entry points and writes correct exports field; manual maintenance drifts |
| .d.ts bundling | Custom tsc wrapper | tsdown `dts: true` (uses rolldown-plugin-dts) | rolldown-plugin-dts handles cross-file type resolution, re-exports, and declaration maps |
| Monorepo workspace linking | Symlinks or path configs | `bun install` with `"workspaces"` in package.json | bun hoists shared deps and links local packages as if they were npm packages |
| Build orchestration | Shell scripts with manual dep order | Root scripts with `--filter` and sequential `&&` | bun `--filter` respects workspace topology; sequential `&&` gives explicit control |
| Per-package test isolation | Separate `bun test` invocations | Vitest `test.projects` array | Single vitest process, shared coverage, correct filtering |

**Key insight:** tsdown's `exports: true` is the critical pattern — it eliminates the most error-prone manual work (keeping package.json exports in sync with actual build outputs).

## Common Pitfalls

### Pitfall 1: Vite Alias Doesn't Cover Subpath Imports
**What goes wrong:** You add `'@gnomad-cf/core': '/path/to/packages/core/src'` to Vite alias, but imports like `import { ... } from '@gnomad-cf/core/calculations'` fail to resolve because the alias is an exact-match replacement, not a prefix replacement.
**Why it happens:** Vite's string-based alias does prefix replacement when the alias string ends without a trailing slash, but the behavior depends on whether Vite treats it as a package name or a path prefix. Different Vite versions behave differently.
**How to avoid:** Test the alias immediately after adding it. If subpath imports fail, use the array syntax with a regex find:
```typescript
resolve: {
  alias: [
    {
      find: /^@gnomad-cf\/core(\/.*)?$/,
      replacement: '/absolute/path/to/packages/core/src$1',
    },
    { find: '@', replacement: '/absolute/path/to/apps/web/src' },
  ]
}
```
**Warning signs:** `Failed to resolve import "@gnomad-cf/core/calculations"` in dev server console.

### Pitfall 2: tsconfig paths and Vite alias Out of Sync
**What goes wrong:** TypeScript sees the correct types (via `paths` in tsconfig), but Vite cannot resolve the import at runtime, or vice versa. This produces "types are correct but the page crashes" or "runtime works but tsc errors".
**Why it happens:** Two separate systems handle resolution: tsc uses `paths`, Vite uses `resolve.alias`. They must point to the same location.
**How to avoid:** Set both identically. The tsconfig `paths` field and Vite `alias` field must map `@gnomad-cf/core` → the same absolute source directory.
**Warning signs:** `Cannot find module '@gnomad-cf/core'` from tsc but page loads fine, or page crashes with module-not-found at runtime despite passing typecheck.

### Pitfall 3: bun --frozen-lockfile Fails in CI After Workspace Restructure
**What goes wrong:** Adding new workspace packages to `package.json` creates lockfile changes. Running `bun install --frozen-lockfile` in CI fails with "lockfile had changes".
**Why it happens:** The lockfile must be regenerated after any workspace structure change. Frozen lockfile strictly enforces that the lockfile matches what would be generated.
**How to avoid:** After restructuring workspaces, run `bun install` locally (not `--frozen-lockfile`) to update `bun.lock`, commit the updated lockfile, then CI will pass.
**Warning signs:** CI fails at `bun install --frozen-lockfile` step with lockfile diff message.

### Pitfall 4: isolatedDeclarations Conflict with Zod-Inferred Types
**What goes wrong:** Enabling `"isolatedDeclarations": true` in `packages/core/tsconfig.json` causes tsc to error on `z.infer<typeof UrlStateSchema>` usage because Zod's inferred types cannot be expressed without the full Zod library types inline.
**Why it happens:** `isolatedDeclarations` requires all exported types to be explicitly declared without inference from complex library types. Zod schemas produce complex conditional types that violate this constraint.
**How to avoid:** Do NOT enable `isolatedDeclarations` in `packages/core`. tsdown works fine without it — it falls back to the TypeScript compiler API for .d.ts generation, which is "reliable" per official docs. Only use `isolatedDeclarations` if performance of the type build becomes a problem AND you refactor away all inferred Zod types.
**Warning signs:** tsc errors like `Type of property 'X' circularly references itself in mapped type` or `Inferred type of 'Y' is not portable`.

### Pitfall 5: apps/web TypeScript Resolving Core Types Through dist/ Instead of src/
**What goes wrong:** During development, TypeScript picks up `.d.ts` files from `packages/core/dist/` (from a previous build) instead of the `.ts` source files, causing stale types after editing core.
**Why it happens:** The `main`/`exports` field in `packages/core/package.json` points to `dist/`. TypeScript resolves from there if project references or path mappings are not set up correctly.
**How to avoid:** Ensure the tsconfig `paths` in `apps/web` explicitly points to the source `.ts` files, not `dist/`. With tsdown `exports: true`, the `publishConfig` pattern points exports to dist, but the development `exports` should point to source when using tsdown `devExports`.
**Alternative:** Rely entirely on the Vite alias for development (bypasses package.json resolution); use TypeScript's `paths` config for editor type checking.
**Warning signs:** Editor shows stale autocompletion for `@gnomad-cf/core` types after editing `packages/core/src/`.

### Pitfall 6: Web Composables Still Import from @/ After Extraction
**What goes wrong:** After moving modules to core, some composables still import via `@/utils/variant-filters` instead of `@gnomad-cf/core/filters`. This silently works (the file still exists in apps/web/src/utils) until you delete the moved files, at which point things break.
**Why it happens:** Incremental migration leaves duplicate files temporarily. The old `@/` paths continue to work because the files haven't been deleted yet.
**How to avoid:** Delete source files from `apps/web/src/` immediately after verifying the core module compiles and the web app still builds. Don't let duplicates linger.
**Warning signs:** After "completing" extraction, `src/utils/` still contains files that should have moved to core.

### fetch-based Core Client Skeleton
```typescript
// packages/core/src/client/index.ts
// Uses standard fetch — works in Node, Bun, and browser
import { getApiEndpoint, type GnomadVersion } from '../config/index.js'

export interface GraphQLRequest {
  query: string
  variables?: Record<string, unknown>
}

export interface GraphQLResponse<T> {
  data?: T
  errors?: Array<{ message: string }>
}

export async function executeGraphQLQuery<T>(
  request: GraphQLRequest,
  version?: GnomadVersion
): Promise<GraphQLResponse<T>> {
  const endpoint = getApiEndpoint(version)
  const response = await fetch(endpoint, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(request),
  })
  if (!response.ok) {
    throw new Error(`GraphQL request failed: ${response.status}`)
  }
  return response.json() as Promise<GraphQLResponse<T>>
}
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| tsup (tsup-first CJS) | tsdown (ESM-first) | 2024-2025 | No more ESM file extension holes; faster builds |
| `vitest.workspace.ts` | `test.projects` in `vitest.config.ts` | Vitest 3.2 | Single config file; workspace API deprecated |
| `bun.lockb` (binary) | `bun.lock` (text JSON) | Bun 1.2 (Dec 2024) | Git-diffable, reviewable, 30% faster cached installs |
| Manual package.json `exports` field | `exports: true` in tsdown | tsdown 0.19+ | Zero manual maintenance; stays in sync with build |

**Deprecated/outdated:**
- `vitest.workspace.ts` or `vitest.workspace.js` files: superseded by `test.projects` in `vitest.config.ts` as of Vitest 3.2
- `tsup`: still functional but tsdown is the recommended successor from the same ecosystem
- `bun.lockb`: still supported by bun but text `bun.lock` is now the default since bun 1.2

## Open Questions

1. **bun.lock vs bun.lockb: current lockfile format**
   - What we know: The project has `package-lock.json` (npm compat), not `bun.lockb` or `bun.lock`. `bun@1.3.9` (pre-1.2 format) may create `bun.lockb`.
   - What's unclear: Which lockfile format will `bun install` create given `packageManager: "bun@1.3.9"`? bun 1.3.9 predates the bun 1.2 text format (text format introduced in bun 1.2 = December 2024, but 1.2 numbering may differ from 1.3.x).
   - Recommendation: On day one, run `bun install` and check whether `bun.lock` (text) or `bun.lockb` (binary) is created. If binary, migrate immediately using `bun install --save-text-lockfile --frozen-lockfile --lockfile-only && rm bun.lockb`.

2. **VitePress docs location after monorepo restructure**
   - What we know: Current `bun run docs:build` outputs to `docs/.vitepress/dist`. After move, docs live somewhere under `apps/web/`.
   - What's unclear: Does vitepress expect to run from the package root? Does `base` path in vitepress config need updating?
   - Recommendation: Keep VitePress docs at `apps/web/docs/` since it documents the web app. Update CI to reference `apps/web/docs/.vitepress/dist`.

3. **tsdown platform: 'neutral' vs 'node' for core**
   - What we know: `platform: 'neutral'` is correct for code that runs in Node, Bun, and browser. The core fetch client uses standard `fetch` (available in all three).
   - What's unclear: Does `platform: 'neutral'` affect how tsdown handles JSON imports (the config JSONs)?
   - Recommendation: Use `platform: 'neutral'` and test that JSON config imports (`import gnomadConfig from './gnomad.json'`) resolve correctly in the built output. Fallback: move to `platform: 'node'` if neutral causes issues with JSON.

4. **`bun run --filter` syntax for ordered build**
   - What we know: `bun run --filter @gnomad-cf/core build && bun run --filter gnomad-cf-web build` gives explicit sequential ordering.
   - What's unclear: Does bun support a `--workspace-build-order` or `--topological` flag that would auto-order by dependency graph?
   - Recommendation: Use explicit `&&` chaining for now. It's clear, debuggable, and proven. Auto-ordering is a future optimization.
